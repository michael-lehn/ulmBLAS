# ulmBLAS benchmark results

This directory archives my benchmark campaigns: measurements of the micro
kernels and the BLAS routines of ulmBLAS on specific machines, compared
with other BLAS libraries.  Each campaign keeps its hardware, software,
source revisions, method, raw data and the scripts for its figures, so the
results stay comparable when new kernels or machines come along.  For an
overview of the results see [PERFORMANCE.md](../PERFORMANCE.md).

## Campaigns

One table per data type.  A campaign appears in the table of every type it
measures (`TYPES` in its `campaign.conf`; without `TYPES` it measures
`double`, as all campaigns up to 026).

## Names and numbers

A campaign is a directory `NNN-DATE-MACHINE-EXPERIMENT`, e.g.
`010-2026-10-26-uc3-icelake-dgemm`.

- `NNN` is the permanent sequence number and the campaign's identity
- `DATE` is the day the measurements were completed; start and end are in
  the campaign's `README.md`
- the number is assigned when the campaign is archived (the highest number
  plus one) and never changes, so links stay valid
- numbers follow the order of archiving, not the dates: several campaigns
  may have the same date, and dates need not increase with the number
- campaigns measured in parallel on different machines get their numbers
  only when they are archived; a lock (`benchmark_results/.add-lock`)
  serializes `make add_benchmark_result` in one checkout, and numbers
  assigned in two checkouts at the same time show up as a conflict in this
  index
- `make check_benchmark_results` checks names, numbers (unique, contiguous
  from 001), the index and all local links to campaigns

The numbers were introduced on 2026-10-27 for the 21 campaigns archived
until then (renamed with `git mv`, contents unchanged).

- these 21 were numbered once in the order of the start of their
  measurements (`start` in `logs/run.log`, otherwise the first timestamp in
  `data/logs/`); neighbouring campaigns are hours apart, so time zones do
  not matter
- 001 has no timestamps; it was committed (2026-10-24 17:58 CEST) before
  the first log entry of 002
- two pairs ran at the same time on different machines and are ordered by
  their recorded start: 011 and 012 (5 minutes apart), 018 and 019 (2
  minutes apart); no order had to be assumed
- references were updated everywhere except in the `data/` and `source/`
  directories, which stay as the historical record with the former names;
  the one path there naming another campaign
  (`009-.../source/summarize-eigen.py`) was updated

## Structure of a campaign

| File or directory | Contents |
|-------------------|----------|
| `campaign.conf`   | metadata for the index: `NAME`, `DATE`, `MACHINE`, `TITLE`, `SUMMARY`, optional `TYPES` (`KEY = value` lines) |
| `README.md`       | experiment, setup, method, results |
| `data/`           | measurements as CSV files (raw outputs may be kept in `data/raw/`) |
| `plots/`          | Gnuplot scripts (`*.gp`; scripts starting with `_` are only loaded by others) and their SVG figures |
| `source/`         | the benchmark programs and scripts that produced the data |

Compiled programs, object files, libraries and other build artifacts are
not archived.

## Adding a campaign

The archive does not run benchmarks.  After a campaign is completed,
prepare its directory as above and run

    make add_benchmark_result BENCHMARK_DIR=path/to/campaign [BENCHMARK_NAME=name]

- `NAME` in `campaign.conf` is given without the number
  (`DATE-MACHINE-EXPERIMENT`, e.g. `2026-11-02-uc3-icelake-dtrsm`); the
  campaign gets the next number, which is written into the archived
  `campaign.conf`
- the date does not influence the number; `BENCHMARK_NAME`, if given, must
  equal `NAME`

The target

1. validates the campaign: metadata (the name must contain the date),
   `README.md`, at least one CSV file and one plot script, no binaries or
   build artifacts;
2. generates all figures with Gnuplot (`GNUPLOT=...` selects the program)
   and checks the SVG files;
3. updates the list of figures in the campaign's `README.md` (between
   `<!-- BEGIN FIGURES -->` and `<!-- END FIGURES -->`, appended if
   missing);
4. copies the campaign to `benchmark_results/NNN-NAME` and regenerates the
   index above from all `campaign.conf` files.

Afterwards run `make check_benchmark_results`.

- nothing in `benchmark_results/` changes unless all steps succeed
- archived campaigns are never overwritten with different data: adding a
  campaign again with the same contents only regenerates its figures;
  different contents under an existing name are rejected
- to regenerate the figures of an archived campaign, use it as
  `BENCHMARK_DIR` (e.g.
  `BENCHMARK_DIR=benchmark_results/001-2026-10-24-heim-avx-fma`)
- the target is independent of the library build and `make check`, and it
  neither commits nor publishes anything

If a campaign has a significant new result, it becomes the first highlight
of its operation and data type in [PERFORMANCE.md](../PERFORMANCE.md)
(newest first, each with hardware, libraries, conditions, main results,
limitations, a figure and a link); older highlights stay below it.
